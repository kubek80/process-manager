# Process Manager

A portal for company processes (request a GCP project, onboard to Akamai…) and standards (rules issued by cyber security, platform owners, practices). It generates skills and pull request review agents from both, searches them by meaning, and serves them to AI agents through an MCP server. React + Vite frontend, Go backend, Postgres. Start with `README.md`; server details are in `docs/backend.md`.

## Always

- **Finish every task that changes code by running the `update-docs` skill**, before the final summary and before committing. The in-app Guide (`src/components/GuidePage.tsx`) is the main documentation and must match the code.
- Run the tests that cover what you changed, and `npm run test:all` before saying a change is done. Add tests with every feature and every bug fix.
- Sample content is edited with the skills `edit-process`, `edit-standard` and `manage-catalog`.

| `npm run test:all` | typecheck, validate, Vitest, Go tests, Playwright |

## Conventions

- **The database is the source of truth** for processes, standards, the lists, roles, feedback, requests, skills and the use counts. The files in `processes/`, `standards/` and `catalog/` are sample content that fills an empty database; changing them does not change a running installation unless they are imported. `demo/` holds a larger demo set in the same layout, loaded only on request; tests count the sample, so new demo content goes into `demo/`, not the sample.
- The formats are `schema/*.schema.json`. The frontend checker (`src/lib/validate.ts`) and the server (`server/internal/schema`) both read them; change a format in the schema, run `npm run validators`, then change the types (`src/types.ts`), the checker, the server's consistency check (`server/internal/docs/check.go`), the prompts and the generators (`server/internal/skills`).
- The lists are teams, pillars, tribes, domains, practices, platforms, categories, tools, architecture patterns, tiers, paths, environments and languages (thirteen); processes and standards refer to them by id. They are two places (`PLACE_LISTS` / `placeOfList` in `src/lib/store.ts`), in the top bar and as two entries of Admin's side menu: Teams (`#/teams/<list>/<id>`: teams, pillars, tribes, domains, practices, platforms) and Tools (`#/tools/<list>/<id>`: tools, categories, patterns, tiers, paths, environments, languages); a new list goes into one of them and into its set of tabs (`GROUPS` in `CatalogPage`, one row of two sets, one set of tabs for the keyboard: `tabAfterKey` in `src/lib/listTabs.ts`). An address of the lists that is not the right one (a list under the other place, an unknown list, the older `#/catalog/…` and `#/admin/lists/…`) is read into the list and entry it means and replaced in place by the right one (`correctedListsAddress` in `store.ts`, used once in `App.tsx`). The search box belongs to the list shown: emptied when the address moves to another list, kept when only the entry changes (`searchStays` in `listTabs.ts`). Admin › Teams and Admin › Tools are ONE `CatalogPage` with ONE draft of the one document: it follows its address (`#/admin/teams|tools/<list>/<id>`, `addressedList`) without remounting, and moves its address to the other place itself when it goes to a problem there; never put a `key` on it, its draft is the page's state. A field that refers to a list also needs the server's refusal to remove a used entry (`stillUsed` in `server/internal/httpapi/content.go`, which also counts the owners and members tied to a team, platform or practice), and a filter in the search (`src/lib/search.ts`) if readers should find by it. Content stored by an earlier version that no longer fits is converted at start in `server/internal/upgrade`.
- A path (Greenfield, Brownfield, Paved path a.k.a. golden path, and any an organisation adds; `"symbol"` one of the built-in pictures, `"alsoCalled"` other names) is named by a process or standard (`"paths"`, document level, like `tiers`) only when it is meant only for that kind of work; none means whatever the path. Drawn only by `PathMark`, `PathMarks`, `PathRoad`, `PathAny` (`marks.tsx`, styles in `src/paths.css` on `--mark-*`, the quiet surface and the brand, never a state). Two meanings, kept apart: the Path filter is "made for" (`NO_PATH` for none), My application's path and the MCP `path` are "applies to" (`appliesTo`, `onPath`). Its names and other names go through `pathWords` / `docs.PathNames` into the word search, the chunk text, the skills' "Meant for the paths" line (only when named) and the MCP headers. `server/internal/upgrade` adds the three entries once to lists without the key `paths`; a list that has the key, even empty, is never given them again.
- An architecture pattern (`patterns`, "Architecture patterns" to readers; `alsoCalled` like a path, no picture) is a **tag** on a process or standard (`"patterns"`, document level): what it is about, never "meant only for". It hides nothing, is not part of My application, has no MCP parameter (the MCP `path` means "applies to"), and its names go into the word search (`patternWords`), the chunk text and the skills' "Architecture patterns" line only when named (`docs.PatternNames`). An installation without the key has none and is given none; with an empty list readers see nothing about patterns (`OPTIONAL` in `CatalogPage`, the editing section only for lists managers).
- Pillars (`pillars`, a team's `"pillar"`), tribes (`tribes`, a pillar's `"tribe"`) and domains (`domains`, a tribe's `"domain"`) optionally group teams; a team never names a tribe (lists of that earlier shape are converted at start and on import by `upgrade.PillarsFromTribes`); all of it optional, never a problem in the checker. A team's, pillar's or tribe's reference must be an entry (`unknownGroupSentence` / `docs.Check`), and `stillUsed` refuses removing one still named inside the lists (it runs before the checker for the lists). They give no rights (`rbac` does not know them) and are not given to agents; there is no filter by them. Where they show is worded in `src/lib/groups.ts` (`partOf`, `placeOf`, `teamSections`, `teamChoices`); with no pillars everything looks as without them.
- Every save is a version. Saves go through `useDraft` (`src/lib/draft.ts`) in the app and `docs.Store.Save` in the server, which refuses a save made from an outdated version; do not add a second way to save. The one addition is the working draft (`server/internal/docs/drafts.go`, `/api/{processes|standards}/{id}/draft` and `/publish`, contract in `docs/backend.md`), built on the same hook: what is not stored as the document itself - changes to a published document, or what a never-published one cannot be stored as yet - is kept there, with a revision of their own, and leaves it only through `docs.Store.Save` (`PublishDraft` for `/publish`, `ReplaceDraft` for a never-published document's `PUT …?draft=R`). Which call Save draft makes is `saveCallOf`, the revision it sends `draftRevisionToSend` (`src/lib/editing.ts`): never a newer one than the person's work came from. While one exists, a person's ordinary save of that document is refused (a review confirmation is not); never save around it. A save that removes a working draft without a version is logged as a discard (`DraftDropped`). A working draft remembers the version it started from (`base`); when the app re-creates one, it sends the version the person's work came from (`rev=0&base=N`), so a newer publish is met as a conflict, never overwritten.
- A process or standard is changed only on the editing screen (`#/p/:id/edit`, `#/s/:id/edit`: `EditFrame`, `EditSession`, `EditProcessPage`, `EditStandardPage`; its rules in `src/lib/editing.ts`). The reader's page edits nothing; it only offers "Edit" and "Mark as reviewed". The editing screen's columns are outline, fields, what readers will see, in that order on the screen and in the page (Tab, screen readers); "Skip to the page" lands on what readers will see (`main.edit-middle`). From 1100 to 1279 px the outline is always the narrow rail and opens over the fields only on demand. The arrows in the head of a step's or requirement's fields and Alt + Page Up / Down go to the item before or after with the keyboard in the same field (`Stepper` in `EditFrame`, its logic in `src/lib/stepping.ts`). From 761 px the editing screen's messages and the checker's list sit over the fields column, placed by `useColumnPlace` in `EditFrame` (`--edit-fields-left`, `--edit-fields-width`, `--edit-bar-bottom` in `edit.css`): a property of that screen, through the shared `notify`, which keeps its place on every other page. Save draft always works: a never-published document (`status: "draft"`) is stored as itself while nothing is to fix and kept in its working draft otherwise, and is published by a save with `status: "active"`; a published one changes only through its working draft. Only a published document can be retired. Retire, unpublish, bring back and delete are explicit actions in its More menu. The example texts a new document, step or requirement starts with live in one list, `EXAMPLE` in `src/lib/edit.ts`; left in, they are to fix before publishing (`exampleIssues` in `src/lib/editing.ts`). The checker speaks of "to fix" and "suggestions"; a refused Save draft or Publish… shows its reason at the top of the checker's list. A problem is worded as an instruction by `issueText` and shown on its own field by `useFieldMarks` (`src/lib/fieldMarks.ts`, shared by `EditFrame` and Admin › Teams / Tools in `CatalogPage`); never build a second wording or marking. `issueText` also words the problems of the lists (kind `"lists"`: the list and the entry by name, else by id, never a path), and a refusal from the server is turned back into the same sentences (`refusalIssues` in `src/lib/validate.ts`, `refusalText`); the JSON view shows the same sentence, with the place in words first and the path only as a detail. Moving and deleting steps go through `src/lib/edit.ts` (`moveStepInFlow`, `nudgeStep`, `deleteStep`): they change the flow, not only the numbering, never ask first, never rename an answer, and say with Undo what changed in the flow (`structureChanges`; the message after a delete or move is `restructureNotice`). The category and the team in the head of a page are worded by `ownedBy` (`src/lib/catalog.tsx`), for the reader's page and for the editing screen's preview (`PreviewFacts`) alike. The editing screen shows its messages through `editNotice` (`Editing.tsx`): one at a time, gone when the screen is left. What Undo and Redo say is `steppedMessage` in `src/lib/editing.ts`. The map's zoom rules are one module, `src/lib/zoom.ts` (`openingZoom`, `fitWhole`, `afterFit`, `scrollToCentre`, `laneColumn`), used by the reader's map, the editing map and the pictures alike; the map's blocks are one Tab stop (arrow keys move between steps). A process drawn in a text (the Guide's charts, the code map's charts, any other) is `ProcessPicture` (`src/components/ProcessPicture.tsx`, drawing with `FlowView`'s `picture` prop), never a `FlowView` of its own: it drags, zooms with its tools and Ctrl + scroll, has Fit and Enlarge, prints whole, and opens by one rule, `pictureZoom` in `src/lib/zoom.ts` (whole at `PICTURE_WHOLE_MIN` or more, else `PICTURE_MIN`, cut, with a faded edge). An item's name may be empty at any moment while editing: every text built from one goes through `itemWords` in `src/lib/diff.ts` ("Step 3 (no name yet)"). The editing screen keeps the draft above an error boundary (`EditingBoundary` in `Editing.tsx`), so a fault never loses work.
- The app runs under a content security policy without `eval` and without inline scripts: no library that builds code at run time.
- The Processes list, the Standards list and the search results share `DocList` / `DocCard` / `Lists.tsx` and `search()` (`src/lib/search.ts`); change the layout, a filter or the card there once, not per page. Their search, filters, order, page and page size live in the address (`ListState` / `SearchState` in `src/lib/store.ts`), so a link shows the same; browser storage keeps only a person's own defaults, and where the address carries the same thing it wins: "Only my bookmarks" and "Only what needs a review" for the tab (`useRemembered`, sessionStorage), and in localStorage the order a person chose (`useRememberedSort`), the page size (`usePageSize`), cards or rows (`useListView`), the search mode (`rememberedMode`) and My application (`pm:profile`, `useProfile`), which a link never carries; a filter value that no longer exists is dropped by `useLinkFilters` (`knownFilters`). Sorting by date (`src/lib/sorting.ts`) reads `meta[id].createdAt` and `updatedAt` from `/api/processes` and `/api/standards`; `meta[id].draft` (unpublished changes) is sent only to those who may work on its drafts.
- Shared parts: `src/components/marks.tsx` (`KindTag`, `LevelMark`, `NoLevelMark`, `LevelBars`, `Fact`, the path marks), `src/controls.css` (`.tabs` > `.tab`, `.seg` > `.seg-item`) and the alert, `src/components/Alert.tsx` (`Alert` with `tone` info / success / warning / problem, `title`, the description as children, `actions`, `role`; `.alert` in `styles.css`, the designer's anatomy, measured by `e2e/alert.spec.ts`); a page uses them, never its own tag, level, tab or notice style. Every notice about the page a person is on is an `Alert` (a lead becomes its title); the floating `notify` messages are of its family (its icon, `AlertIcon`). Quiet asides (`--quiet`), a field's own problem line, empty states and Theming's notes beside a colour are not alerts. A chosen segment is raised and outlined, not filled: the main-button fill (`--action-fill`) is for the one main button of a view; outlined buttons are "Other buttons" (`--action-other*`). Search highlights use `--search-mark`, which does not follow the brand. Dates and times go through `src/lib/dates.ts` (`formatDate`, `formatDateTime`), never the browser's locale or `slice(0, 10)`. A day is the reader's own: `today` and `dayOf` in `dates.ts` are the only way to get one (a unit test fails on a day built by hand in `src/` or `scripts/`), `daysBetween` / `addDays` / `addMonths` count with it; a day stored in a document (`lastReviewedAt`, `updatedAt`) is shown as written, never shifted. A review records the person's day: the app sends `?day=`, the server takes it while it is today somewhere on Earth (`docs.TodaySomewhere`), else its own UTC day, and never moves the review date back. What has no reader counts in UTC days: the MCP server, `npm run reviews` and the statistics. Media queries a page reads in code and printing go through `src/lib/media.ts` (`useMedia`, `usePrinting`, `printedLine`) and `src/print.css`. One vocabulary: a process is Mandatory / Recommended / Optional, a requirement Must / Should / May; a level is never in the problem colour; review due is a warning, overdue a problem.
- Theming (Admin › Theming): `src/lib/theme.ts` works out the colours, `server/internal/theme` stores only what the admin chose (`portal_settings`). Every colour goes through a token: `--accent` for text, links and outlines, `--accent-fill` with `--accent-ink` for filled surfaces, `--action-fill` / `--action-ink` for main buttons, `--action-other`, `--action-other-line`, `--action-other-soft` for other buttons, `--good` / `--warn` / `--bad` / `--info` with their `-bg`, `-fill`, `-ink` for states (`-on-dark` variants on the editing bar), the kind tokens (`--kind-process-*`, `--kind-standard-*`) for processes and standards, the ground worked out from the ink and the second colour (`--bg`, `--surface*`, `--line*`, `--text*`, `--seg-on` under a chosen segment, tab count, chip or page number, `--control-line` the 3:1 outline of inputs and chips, `--bar*`), the tints `--ocean-10/35/75/100` and `--sky-10/35/75/100` (backgrounds, lines and marks only, never text), `--highlight` / `--search-mark`, `--quiet*`, the alerts' `--alert-info|success|warn|bad-bg` and `-icon` with `--alert-text` (the designer's values in the default look, `ALERT`; information is the second colour's family, not the brand's), the marks that are no state `--mark-green|brown|sky` (with `-bg`), the map's `--step-*` and `--lane-*` (`stepMeta.ts` holds no colour literal), and `--font-family` for type; nothing that should follow the brand or a state is a colour literal. The default look is the designer's palette (`DESIGNER`, `DEFAULT_LOOK`): every fallback in `styles.css` equals `derive(DEFAULT_LOOK)`, every pair a look produces is in `readingPairs`, worked-out text aims at `TEXT_MIN` (4.7) (`themeDesigner.test.ts`). Ready-made palettes set only the brand and the kinds. Type: body text only `--fs-sm|md|lg` with their `--lh-*` (12/16, 14/20, 16/24) and `--fw-regular|medium|strong`, headings `--fs-h4` … `--fs-display`, never regular; every size, weight and line height in every stylesheet but `print.css` and in components is a token (`typeScale.test.ts`); the scale is not a setting. Fonts ship with the app (`@fontsource-variable/*`): Roboto the default, Inter a choice loaded only when chosen; nothing comes from another host.
- The first review is counted from first publication: `reviewOf` / `needsReview` in `src/lib/lifecycle.ts` with `meta[id].publishedAt`, used by every page, counted from the reader's day of `publishedAt`; the MCP server (`server/internal/mcpserver`) decides the same, in UTC days.
- Views, bookmarks, upvotes and skill downloads live in `server/internal/engagement`, requests in `server/internal/requests`; in the app the first are read only through `useEngagement` (`src/lib/engagement.tsx`); the calls for requests and statistics are in `src/lib/store.ts`, their logic in `src/lib/requests.ts` and `src/lib/statistics.ts`. Counts, bookmarks, votes and requests must never reveal a draft or anything else the person may not see, and nobody is ever shown who viewed or downloaded what.
- Admin › Activity shows the log in words from `src/lib/activity.ts` (`ACTION`, `describeEntry`): every action the server writes needs words there and in the list in its unit test (`src/lib/__tests__/activity.test.ts`).
- The places of the top bar are one list (`places` in `src/App.tsx`), used by the desktop bar and by the Menu that replaces it below 1120 pixels; add a place there, not in either.
- Rights are enforced in the server (`server/internal/httpapi`, `server/internal/rbac`); the frontend only hides controls, and works out what to show only in `src/lib/rights.ts`. There is no editor mode: every control appears by rights alone. A process or standard can be changed and published through its platform or practice (`platform-owner`, `practice-owner`) and drafted by their members (`platform-member`, `practice-member`), not through its owning team. Drafting versus publishing is decided only by `canDraft` / `canPublish` / `publishPlaces` (`rights.ts`) and `CanDraft` / `CanSeeDraft` / `Misplaced` / `MisplacedDraft` (`rbac`); a first publication needs an owner of its whole placement (every platform and practice it names) or an editor. Who sees a draft is worded only by `draftAudience`. People are shown by `personLabel` (`src/lib/members.ts`) and `PersonLink`: by name where known, else by address. Admin › Access sets a person's complete set of roles with `/api/admin/users` (`src/lib/users.ts`); `/api/admin/access` gives or takes one role (the Owners and Members sections); both keep the last admin. Owners are given by admins only; the members of a platform or practice also by its owners, and a group's details also by its owners (besides admins and lists managers), only through `/api/groups/…` (`server/internal/httpapi/groups.go`; details saved by `docs.Store.Save` as a version of the lists).
- Viewing as another person (admins; `server/internal/httpapi/viewas.go`, `auth/viewas.go`, table `viewing_as` under the cookie's `sid`; app `ViewAsBand.tsx`): the person of a request is decided only in `signedIn` → `viewedAs`, so every route sees the viewed person's identity and rights; every request but `GET`/`HEAD` is refused in that one place (`guard` → `refuseWhileViewing`), apart from stopping and signing out by exact path. Never add a second place that works out the person or lets a change through. Nothing is ever written in the viewed person's name: a `GET` that writes (a count, a brake) uses `mayCount` / `countsFor`; Activity records only the admin's `viewas.*`. Every change from the app carries `X-Acting-As` (`changeHeaders` in `store.ts`); a mismatch is 409. In the app, controls that change something stay visible, disabled with `useChangeBlocked`'s sentence, and the editing screen never mounts (`pageWhileViewing`, `opensChange` from the router). `reader@no-roles.invalid` is the reader with no roles and can get no role.
- A team's, platform's or practice's page is `GroupPage` (`#/team|platform|practice/:id`), its logic and the rows of the list of teams in `src/lib/groups.ts`; a pillar's, tribe's or domain's page is its sibling `ClusterPage` (`#/pillar|tribe|domain/:id`, logic `clusterContents` / `clusterFilter` in `groups.ts`), showing what its teams own through `GroupPage`'s own `GroupDocs`, never a second search or draft rule; contact details are edited only with `ContactFields`. Links people type are `http(s)` only, checked in the schema (`$defs/contacts`), the server (`docs/contacts.go`) and the app (`isWebLink`), opened with `rel="noopener noreferrer"`.
- The code map (Admin › Code map, `#/admin/code`) lives in `src/codemap` (`types.ts` the format, `index.ts` the areas and categories, `categories/{id}.ts` one file per category; logic in `src/lib/codemap.ts`, page `CodeMapPage.tsx`). It is the one place of the app written for developers: names of files, tables and functions are right there. `src/codemap/__tests__/codemap.test.ts` keeps it true: every path exists, every anchor (`at`) is text of its file, the charts hold together, and every source file (server Go and SQL, `src/` code and styles, `scripts/`, `schema/`, `e2e/`, `deploy/`, the workflows, `Dockerfile` and the other top files) is in at least one category, so a new file fails it until it is placed. A requirement is anchored on the line that enforces the rule; changing a rule means changing its sentence there too. The source itself is served only by `GET /api/admin/source` (`server/internal/httpapi/source.go`): admins only, only files git tracks in the checkout `PM_SOURCE_DIR` names, by an allow-list of paths; it is never bundled into the app (the map's own text is), and a deployment does not set `PM_SOURCE_DIR`.
- Skills and review agents are generated by templates in Go, never by an LLM, so they are repeatable.
- Search by meaning (`PM_EMBEDDINGS`, off by default; `npm run dev` and the tests use `builtin`): `server/internal/chunking` cuts documents into parts, `server/internal/embedding` turns them into vectors, `server/internal/retrieval` keeps the index in pgvector and searches it; the page side is `src/lib/meaning.ts`. The index follows saves in the background through `syncSkills` → `syncIndex` (`server/internal/httpapi/content.go`): a new way to change a document must call it too. A save never waits for the index, and nothing waits for the provider while holding a database connection. Its tables are created by the index's `Ensure`, not by a migration file (the migrations must work without pgvector), and every use of the vector type, its operators and operator class is qualified with the extension's schema. A field worth finding goes into the chunk text in `server/internal/chunking` as well as into the word search (`src/lib/search.ts`).
- The MCP server (`server/cmd/mcp`, `server/internal/mcpserver`, contract in `docs/mcp.md`) reads the portal's database and only searches the index, never builds it.
- Drafts of every kind, a never-published document and any working draft, are never indexed, never returned by `/api/search`, never in skills and never given to agents (a working draft also never in counts, history or exports); to whoever may not see it, a draft must look like something that does not exist - also a draft's skill (the withdrawn skill of a document taken back to draft: left out of `/api/skills`, `404` on its own routes, its download never counted) and the feedback on a draft (`404` also to its author).
- Tools and languages can name an icon (`"icon"`: the SHA-256 of the image). Icons are checked and stored by `server/internal/icons` (an allow-list for SVG in `svg.go`: keep it an allow-list, with nothing that repeats parts of a drawing - no `<use>`, `<symbol>`, `<pattern>`, `href`), served by `/api/icons/{id}` and shown with `EntryIcon`; their files are `catalog/icons/<id>.<ext>`.
- Nothing in tests or CI may call an outside service: Vertex AI is tested against a local stand-in only.
- Text shown to users is written for business analysts: plain words, no implementation terms.
- `deploy/cloudrun/` (Cloud Run behind IAP; steps in its `README.md`) names settings, the port, `/healthz` and the build output: change it with them.
- Go: `gofmt` and `go vet` clean. Database tests use a real Postgres through `dbtest.NewPool`.
